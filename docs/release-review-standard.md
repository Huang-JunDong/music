# 商业化上线审核标准（Release Review Standard）

> 版本：3.2（2026-09-05 七次修订：多用户浏览器级凭证架构对齐——2.2 双轨凭证总则（服务端全局存储 + 浏览器 HttpOnly 会话 Cookie）、2.5 缓存键凭证指纹强制判例、第 1 章风险表补"多用户会话"行；历史：3.1 R1 整改经验反哺——2.7 资源全本地化总则与 vendor 管理要求、5.1 超时默认值、5.3 类型豁免禁令与生成代码要求、附录 B/C 补充；3.0 聚焦代码审核删运维/商务章节、2.1 双端一致性、2.0 业界标准对标、1.2 前后端/协同三章）
> 适用范围：本项目所有计划对外（商业化/生产环境）发布的暂存变更（git staged）及后续迭代。
> 使用方式：每次上线前，审核人按本标准逐项核查并填写《上线审核报告》（模板见附录 C），归档至 `docs/release-reviews/`。

## 0. 审核流程与角色

### 0.1 流程

```
预审（范围与风险分级，定 L1/L2/L3 审核深度）→ 详审（按第 2-7 章清单逐项核查）→ 整改复审 → 批准/驳回 → 上线后跟踪（72h 内问题回收）
```

| 阶段 | 时机 | 产出 |
|---|---|---|
| 预审 | 代码暂存后、提审时 | 变更范围清单 + 风险分级 + 审核深度（附录 A/E） |
| 详审 | 预审通过后 | 逐项 checklist 结论 + 问题清单（P0-P3） |
| 整改复审 | P0/P1 修复后 | 复审记录（仅复核问题项） |
| 批准 | 全部 P0 清零、P1 有结论 | 报告签署（附录 C） |
| 上线后跟踪 | 上线后 72 小时内 | 问题回收记录；严重问题回滚或热修 |

### 0.2 角色与职责

| 角色 | 职责 |
|---|---|
| 审核人（前端） | 第 4 章前端清单 + 第 6 章协同项前端侧 |
| 审核人（后端） | 第 2、3、5 章后端清单 + 第 6 章协同项后端侧 |
| 发布负责人 | 汇总结论、批准上线或驳回；第 7 章兼容性终审 |

### 0.3 问题严重级别定义

| 级别 | 定义 | 处置 |
|---|---|---|
| **P0 阻断** | 可被未授权用户利用的漏洞；用户数据泄露 | **必须清零方可上线** |
| **P1 高危** | 安全弱点需组合条件利用；核心链路功能不可用；数据损坏风险 | 上线前必须修复或有书面风险接受 |
| **P2 中危** | 输入校验缺失、性能隐患、交互缺陷、兼容性缺口 | 限期修复（下一迭代） |
| **P3 低危** | 代码质量、样式细节、文档、优化建议 | 记录跟踪（技术债登记表） |

## 2. 安全（对齐 OWASP ASVS L1-L2）

### 2.1 认证与授权（ASVS V2/V4）
- [ ] **所有**新增 API 路由均接入 `requireAuth`（或明确豁免理由并记录）；用 `app/api` 全量扫描核对，禁止遗漏。
- [ ] 未授权用户不可触发携带他人登录态（Cookie/Token）的请求。
- [ ] `MUSIC_DL_DISABLE_AUTH=1` 不得出现在生产环境配置。

### 2.2 会话与凭据（ASVS V3）
> **双轨凭证架构总则（v3.2）**：音源凭证存在两条合法通道——① 服务端全局存储（SQLite `cookies` 表 / QQ credential，管理员配置，全站兜底）；② 浏览器级会话 Cookie（`music_dl_src_<source>`，HttpOnly，访客扫码登录自己的账号，请求级会话优先于全局存储，写入改道回浏览器）。审核时先判定变更落在哪条通道，再套用对应核查项；两通道均禁止向**非凭证持有者**泄露明文。

- [ ] 服务端存储的第三方 Cookie/Token（SQLite `cookies` 表、`data/*.json`）仅服务端可读，不通过任何 API 明文回显给前端（脱敏读取）。
- [ ] **浏览器级音源凭证（`music_dl_src_*`）**：必须 HttpOnly + SameSite + 有限 Max-Age；提供清除通路（DELETE 接口）；登录流程中向凭证持有者本人的回显（如 qr 轮询成功响应，key 仅会话创建者持有）可豁免但须登记；访客凭证不得落服务端存储（隐私最小化）。
- [ ] 上游 Set-Cookie 透传浏览器时：加 `HttpOnly`、限定 `Path`、评估是否必须。
- [ ] 会话 Cookie 签名算法、过期、防重放符合 `lib/auth.ts` 既有标准。

### 2.3 注入与输入校验（ASVS V5）
- [ ] 所有 query/body 参数有类型与范围校验（白名单/上限），拒绝异常输入（400 而非透传上游）。
- [ ] 文件上传：大小上限、类型白名单、文件名消毒（防路径穿越，`sanitizeFilename` 覆盖所有落盘路径）。

### 2.4 SSRF 与出站请求
- [ ] 用户可控的 `proxy` / `realIP` / 任意 URL 参数必须白名单化或禁用。
- [ ] 出站请求禁止 `rejectUnauthorized: false`（除非书面风险接受）。
- [ ] 服务器不得可被用作访问内网/第三方身份的开放代理。

### 2.5 缓存与多用户隔离
- [ ] 响应缓存 key 必须包含用户/会话维度，或仅缓存无个性化数据；登录态响应一律不缓存。
- [ ] **凭证指纹强制判例（v3.2）**：进程内代理缓存（如 netease apicache、qq LRU）缓存 key 必须附带"生效凭证指纹"（cookie md5 / credential sha1 截断），游客/全局/各浏览器会话各自缓存互不回放；显式传 cookie 的请求一律不读不写缓存（对齐 `app/api/netease/[...path]` 与 `app/api/qq/[...path]` 实现）。
- [ ] 任何缓存不得跨用户回放含个人信息（账号、私信、VIP 资源）的响应。

### 2.6 密钥与敏感常量
- [ ] 代码中硬编码常量逐一登记：来源、性质（公开客户端常量 or 机密）、泄露影响。
- [ ] 机密（数据库口令、WebDAV 凭据、代理凭据）仅经环境变量/密钥管理注入，禁止入库入仓。

### 2.7 依赖与动态执行
- [ ] 新增依赖：来源可信、维护活跃、无已知高危漏洞（`npm audit`）；用途与体积合理。
- [ ] 运行时动态加载/执行远端脚本的（如 jsdom `runScripts:"dangerously"` + CDN JS），必须固定版本/校验哈希，否则 P1。
- [ ] **资源全本地化**：所有 npm 包与 js/css/html 资源一律本地加载（bundle 打包或 vendor 入库），项目中不得存在运行时从 CDN/远端 URL 加载执行的脚本、样式、页面（含 `<script src>`/`<link>` 远端引用、动态 `import("https://…")`、`new Function(远端串)`）；数据 API 抓取（如拉取 HTML 解析取数、不执行）须与资源执行严格区分并在报告中登记。
- [ ] **vendor 第三方脚本管理**：入库的第三方脚本须登记来源 URL、字节数、SHA-256 指纹常量，读取时校验指纹，更新必须走 git 审查（参照 `lib/netease/vendor/dun-tool.min.js` 范式）。
- [ ] **沙箱执行收紧**：jsdom 等沙箱执行环境禁用外部子资源加载（不得使用 `resources:"usable"`），脚本以内联 `textContent` 注入；功能因此降级可接受（须有 catch 降级路径）。
- [ ] **不可达分支判例**：动态执行代码虽当前不可达（如依赖未安装）但仍在库中，仍计 P1——除非显式移除该路径或在文档声明不支持。

### 2.8 前端安全（OWASP Top 10 A03 注入）
- [ ] 用户/API 响应内容渲染无 `dangerouslySetInnerHTML`；JSON 以文本呈现。
- [ ] 写操作（POST/DELETE）校验同源与 XHR（沿用 `lib/write-guard.ts` 模式）。

### 2.9 限流与滥用防护
- [ ] 对外接口具备 IP/会话级速率限制与并发上限；代理转发类接口必须有配额。

## 3. 隐私与数据保护（最小化原则）

- [ ] 个人信息（手机号、账号资料、私信、听歌记录）处理遵循最小化原则；不落盘非必要字段。
- [ ] 日志脱敏：`logger` 不得输出完整响应体（含个人信息）、Cookie 值、Token；错误日志仅记录 code/msg/trace 标识。
- [ ] 本地数据目录（`data/`，含 SQLite、匿名 token 文件）权限最小化。
- [ ] 提供"删除我的数据"能力：账号 Cookie、缓存、下载记录可清空。

## 4. 前端审核标准

> 适用栈：React 19 + Tailwind v4 + zustand + motion + lucide-react + sonner。可用性对齐 ISO 25010 Usability 与 WCAG 2.1 AA。

### 4.1 交互逻辑
- [ ] **状态管理**：服务端数据经统一客户端层（`lib/client/`）获取；全局状态（播放器等）走 zustand 单一数据源；禁止组件内复制服务端状态形成双源不同步。
- [ ] **异步四态**：每个数据加载视图齐备 loading / error / empty / success 四态；error 有重试入口，empty 有引导文案，不得白屏或静默失败。fetch 消费前必须校验 `r.ok`（非 2xx 一律走 error 态，401 给登录引导文案），数据进入 state 前校验关键结构（如 `categories` 字段存在），防异常响应体被当数据渲染导致整页崩溃。
- [ ] **竞态防护**：搜索/轮询类连续请求有防抖或键控取消（最后写入胜出）；页面切换或参数变更时旧响应不得覆盖新视图。
- [ ] **表单与输入**：动态参数行（增删/回车提交）、非法值即时校验反馈；提交中防重复点击（sending 态禁用）。
- [ ] **键盘与焦点**：全局快捷键（空格播放等）不与输入框冲突（聚焦输入时不触发）；弹层/抽屉有焦点管理与 Esc 关闭。
- [ ] **导航集成**：新页面接入 `components/shell/app-shell.tsx` 的 NAV（PC 侧边栏 + 移动底部 Tab），含图标、active 匹配规则（`match` 前缀）、直达 URL 可刷新还原状态（分享/收藏的深层路由可直达）。

### 4.2 样式
- [ ] **设计令牌一致**：颜色/间距/圆角/字号使用既有暗色 tokens 与 Tailwind 工具类；禁止散落硬编码色值与 magic number。
- [ ] **响应式**：PC/移动双布局遵循既有断点模式（表格 ↔ 卡片）；触控目标 ≥44px；横向滚动可控；双端深度核查见 4.4。
- [ ] **动效**：motion 动画遵循 `prefers-reduced-motion`（沿用 `useReducedMotion` 模式）；时长/缓动与全局一致，动画不阻塞交互。
- [ ] **主题与对比度**：暗色主题下文字对比度达 WCAG 2.1 AA（4.5:1）；等宽代码区（JSON 响应等）与正文字体层级分明。
- [ ] **布局稳健**：长文本/长 URL/大 JSON 有截断、省略或滚动容器，不撑破布局；骨架/占位与最终内容尺寸接近，无跳动（CLS 可控）。

### 4.3 功能
- [ ] **操作反馈**：复制、保存、删除等操作经 sonner toast 给予成功/失败反馈；耗时操作有 spinner（Loader2 模式）。
- [ ] **错误呈现**：接口非 2xx 时展示状态码与可读错误信息（对齐 `/netease` 控制台 status/duration/body 模式），不吞错。
- [ ] **文案规范**：界面中文文案统一（含标点）、按钮动词明确、空态/错误文案可操作。
- [ ] **可访问性（WCAG 2.1 AA）**：图标按钮有 `aria-label`；列表/表单用语义化标签；颜色不是唯一信息载体；焦点可见。
- [ ] **媒体集成**：涉及播放的功能接入全局播放器（队列/换源/MediaSession），不另起 `<audio>` 破坏单一播放实例。

### 4.4 双端一致性（PC / 移动全覆盖）
> 本项目为响应式 Web（非独立 App），双端共用代码库，任何前端变更必须同时在两种形态下验证。

**布局与导航**
- [ ] 断点行为明确：PC 侧边栏布局 ↔ 移动底部 Tab + mini 播放条切换无错位；同一状态双端结构对齐（表格 ↔ 卡片逐列核对）。
- [ ] 窄窗口连续拉伸（1200→768→375px）无破版、无横向滚动条（除声明容器）；移动横屏可用。
- [ ] 全屏播放页/弹层在双端各自可用：PC 居中/侧滑，移动底部抽屉，关闭手势/按钮齐备。

**交互差异**
- [ ] 无 hover 依赖：PC 上 hover 展示的信息/操作，移动端有点击或长按等价入口（信息不得仅 hover 可达）。
- [ ] 触控目标 ≥44×44px 且间距充足；手势（滑动切歌/删除、下拉刷新）不与页面滚动/播放器进度条冲突。
- [ ] PC 键盘路径（Tab 焦点序、Enter 提交、快捷键）与移动触控路径功能对等；焦点可见双端一致。

**移动端专项**
- [ ] 软键盘：输入框聚焦不被键盘遮挡（自动滚动可见）；iOS 输入框字号 ≥16px 防自动放大；键盘收起后布局复位。
- [ ] 安全区与视口：刘海屏 `env(safe-area-inset-*)` 适配；地址栏收展用 `100dvh`（禁裸 `100vh`）；无意外双击缩放。
- [ ] 滚动锁定：弹层/抽屉打开时背景不可滚动，关闭后恢复；下拉刷新不误触。
- [ ] 播放连续性：锁屏/后台播放、系统媒体控件（MediaSession：播放/暂停/上一首/下一首/进度）、耳机线控/蓝牙断连暂停、来电中断恢复——真机验证。
- [ ] 自动播放策略：首次交互前不强制自动出声（静音或用户触发）；逐字歌词高亮在移动端不掉帧。

**双端功能对等**
- [ ] 功能清单对等：新增功能在双端均可用或明确声明"仅 PC/仅移动"并在报告中记录理由；隐藏差异视为 P2。
- [ ] 状态一致性：队列、收藏、下载记录等双端展示同一数据源，无端特有脏状态。
- [ ] 文案/图标/空态双端一致（同一组件变体，不允许两套拷贝）。

### 4.5 组件架构与复用
- [ ] **复用优先**：新 UI 优先复用既有组件（`PageHeader`、`song-list`、`playlist-grid`、播放器组件），禁止复制粘贴改造形成平行组件；确需新组件时评估是否下沉为共享件。
- [ ] **职责单一**：组件单职责（展示/容器分离），页面级组件不混入可复用逻辑；超过 300 行的组件评估拆分。
- [ ] **Props 契约**：props 显式 typed（interface 定义），回调命名 onXxx、布尔避免连环嵌套（超过 3 个布尔改配置对象）；禁止 props 透传链超过 2 层。
- [ ] **目录归属**：仅单页使用的组件留在页面目录，跨页共享进 `components/`；工具函数不写在组件内。
- [ ] **"use client" 边界**：客户端组件最小化，能用服务端组件/静态渲染的部分不加 "use client"；不因图省事整页客户端化。

### 4.6 状态与数据流
- [ ] **store 设计**：zustand store 按领域拆分（播放器/队列/UI 态），单一 store 单一职责；持久化（localStorage）范围明确且白名单字段，不持久化临时态。
- [ ] **订阅粒度**：组件用 selector 订阅最小切片，禁止整个 store 对象订阅导致大范围重渲染；派生数据用 `useMemo`/selector 计算。
- [ ] **失效与刷新**：写操作后的列表刷新通路明确（下载完成→记录列表、收藏→歌单），不允许靠用户手动刷新兜底；批量写完成后一次性刷新而非逐条。
- [ ] **URL 即状态**：可分享/可回退的状态（选中分类、搜索词、页码）进 URL query，浏览器前进后退可用。
- [ ] **时区与时间**：时间展示统一本地时区格式，不混用 UTC 字符串直出。

### 4.7 渲染性能
- [ ] **长列表**：1000+ 行的歌单/记录列表有虚拟化或分页/懒加载，首屏 DOM 数量可控。
- [ ] **重渲染控制**：列表项组件 `memo` 化；行内回调引用稳定（`useCallback`/store action），key 用稳定业务 id（禁止数组索引 key 配合增删）。
- [ ] **动画性能**：动画只动 `transform/opacity`（不触发布局属性 width/top）；动画帧率双端实测不掉帧；长列表滚动中不触发逐行动画。
- [ ] **图片**：封面/大图懒加载（`loading="lazy"`）+ 明确宽高占位防跳动；不失真拉伸（object-fit）。
- [ ] **包体**：新页面不影响首屏（代码分割自动）；重量级依赖（motion 大特性、图表库）按需动态 import；bundle 体积对比上版无异常膨胀（>20% 需说明）。
- [ ] **防抖节流**：搜索输入、窗口 resize、滚动监听有防抖/节流。

### 4.8 副作用与生命周期
- [ ] **清理完备**：`useEffect` 中事件监听器、定时器、`AbortController`、MediaSession 处理器在依赖变更/卸载时清理，无累积监听。
- [ ] **音频单例**：全局仅一个 `Audio` 实例（播放器 store 管理），页面卸载/路由切换不断播且不重复播放；换源保持进度策略明确。
- [ ] **依赖数组正确**：effect 依赖完整（lint exhaustive-deps 无告警）；不应在 render 期间做副作用（事件绑定、数据请求）。
- [ ] **全局注入收敛**：`bindAudioEvents`/`bindSpaceToggle` 类全局绑定只初始化一次，多处调用幂等。
- [ ] **内存泄漏嫌疑排查**：闭包持有大对象（整页歌曲数据）在卸载后可达性断开；长驻页面（播放页）切换无内存持续增长迹象。

### 4.9 错误边界与降级
- [ ] **ErrorBoundary**：路由级/关键区块级错误边界存在，子树崩溃不白屏整页（展示错误卡 + 重试/返回）。
- [ ] **局部降级**：非核心区块（封面、歌词译文、推荐位）加载失败不阻断核心内容渲染。
- [ ] **异常上报**：前端运行时错误有统一捕获入口（console.error 或上报通道），不静默吞掉。
- [ ] **骨架与占位**：结构性大区块（列表/网格/播放器）有骨架屏，避免布局跳变与长时间空白。

## 5. 后端审核标准

> 适用栈：Next.js Route Handlers（Node runtime）+ better-sqlite3（SQLite）+ 原生 fetch/undici。对齐 ISO 25010 Functional Suitability / Performance、REST 语义。

### 5.1 接口设计
- [ ] **路由与方法语义**：路径命名与既有 `/api/*` 风格一致（小写/复数资源/动作用动词段）；读 GET、写 POST、删 DELETE；`runtime="nodejs"` 与 `dynamic="force-dynamic"`（涉库/鉴权路由）显式声明。
- [ ] **写操作守卫**：POST/PUT/DELETE 走 `lib/write-guard.ts`（POST + XHR + 同源）；敏感操作叠加 `requireAuth`。
- [ ] **状态码语义**：400 参数缺失/非法、401 未登录、404 资源不存在、5xx 服务端错误；上游业务码（如 301 需登录）映射为明确 msg，不把上游 5xx 原样透传造成歧义。
- [ ] **响应结构统一**：JSON 结构与既有 API 一致（错误体 `{ error }` 或 `{ code, msg }` 二选一并全局统一）；分页接口返回 `{ items, total, page, pageSize }` 模式。
- [ ] **参数校验**：必填/类型/枚举/范围逐项校验，先拒绝后处理；`limit/offset` 有硬上限；非法输入 400 带字段名。
- [ ] **超时与错误分类**：出站请求必有超时，**默认值 10-15s**（禁止 `Number(x) || 0` 语义下无超时）；用户可传 `timeout` 参数必须 clamp 合理区间（如 1-30000ms）；捕获区分网络错误/上游业务码/解析失败三类，分别映射响应。

### 5.2 数据库交互
- [ ] **参数化查询**：一律 prepared statement（`?` 占位）；禁止字符串拼接 SQL（含 ORDER BY/列名动态拼接需白名单）。
- [ ] **语句复用**：热路径 prepared statement 缓存复用，不在循环内重复 prepare；批量写入用 `transaction()` 包裹。
- [ ] **同步 API 阻塞评估**：better-sqlite3 为同步调用——新查询必须在毫秒级返回；全表扫描/大数据量操作分页或后台任务化，禁止阻塞事件循环拖垮并发请求。
- [ ] **迁移兼容**：schema 变更幂等（`IF NOT EXISTS` / 条件 ALTER），兼容既有 `data/app.db`；删除/重命名列需双写过渡或一次性转换脚本；迁移失败不破坏旧库（可回滚）。
- [ ] **索引与性能**：新增查询路径核对 WHERE/ORDER BY 命中索引；规避 N+1（循环内查询合并为 JOIN 或 IN 批量）。
- [ ] **写竞争**：启用 WAL / busy_timeout；并发写场景（下载去重、播放缓存）有唯一约束或 upsert 兜底。
- [ ] **数据生命周期**：新表/新列纳入既有清除通路（如下载记录清空、Cookie 删除）；凭据类字段不落明文日志。
- [ ] **连接与初始化**：`getDB()` 单例模式不重复打开；表初始化集中在启动/首次访问路径，失败有明确错误。

### 5.3 分层与业务逻辑
- [ ] **薄路由**：Route Handler 只做"解析 → 校验 → 调用服务层 → 格式化响应"；业务规则集中在 `lib/` 服务模块，禁止在路由内堆砌业务逻辑（复用与测试需要）。
- [ ] **单一实现**：同一业务能力（如相似度匹配、文件名生成）只有一处实现（`similarity.ts`、`web-core.ts` 模式），禁止路由间各写一套。
- [ ] **纯函数优先**：无副作用的数据加工（排序/过滤/格式化）写成可单测的纯函数，与 IO 分离。
- [ ] **常量集中**：魔法数字/阈值（超时、上限、权重）提为具名常量并注释来源，不散落函数体内。
- [ ] **类型严谨**：公共函数显式返回类型；`any` 仅限与上游交互的边界处且收敛在 adapter 层（如 `axios-compat`），内部传递立即收窄。
- [ ] **禁止整文件类型检查豁免**：`@ts-nocheck`、文件级 `eslint-disable`、批量 `@ts-ignore` 一律不允许（实证：3 个运行时 bug 借此逃逸 tsc，移除后一次暴露 119 个错误）；确需豁免的逐行 `@ts-expect-error` 并附原因。
- [ ] **自动生成/移植代码**：生成物须有完整性测试锚定（如 439 注册表测试防遗漏/防路由漂移）；生成脚本自身纳入审核范围——"顶层辅助变量前缀隔离"类转换约定须在脚本内实现并在重生成时校验（漏生成 `typeMap` 即此类缺陷）；adapter 层（axios-compat 等）的调用面需与被仿对象核对（可调用性/方法签名），防直调误用。

### 5.4 并发与异步
- [ ] **聚合模式**：多源/多步并发用 `Promise.allSettled`（对齐 `/api/search` 聚合模式），部分失败不整体失败，错误按源归入 `errors` 字段返回。
- [ ] **异常冒泡**：async 函数不吞 rejection（`catch {}` 必须注释原因）；模块以 `{ status, body }` 对象抛出业务错误的既有模式保持一致，路由层统一接住。
- [ ] **子进程治理**：ffmpeg 调用有超时 kill（防僵尸进程）、并发上限、stderr 收集上限；进程退出码校验后才认定成功。
- [ ] **后台任务**：启动扫描类任务（`instrumentation` 模式）不阻塞启动、失败可重入、重复触发幂等。
- [ ] **单飞并发**：同类惰性初始化（匿名 token 注册模式）用共享 Promise 防并发重复执行。

### 5.5 流式与大负载
- [ ] **流式转发**：音频/大文件代理必须流式（Range/206 透传），禁止整块 `arrayBuffer()` 缓冲到内存；背压（reader 慢于 writer）场景不堆积。
- [ ] **请求体上限**：multipart 上传有大小上限与字段数上限；超限返回 413 而非 OOM。
- [ ] **响应体防护**：代理/透传上游响应有截断或体积校验（对齐控制台 400KB 截断模式）；Content-Type 与实际内容匹配。
- [ ] **分块下载**：并行分块（range-fetch 模式）有短读校验与失败重试，块大小与并发数可配置。

### 5.6 文件系统
- [ ] **路径安全**：一律 `path.join`/`path.resolve` 构造（禁止字符串拼 `/`）；用户可控文件名经 `sanitizeFilename` + 相对路径校验（解析后必须仍在目标目录内）。
- [ ] **原子写**：重要文件（token、设置）临时文件 + rename 原子落盘；写失败不留半成品。
- [ ] **资源释放**：`fs.open` 的 fd 必须 close（try/finally 或 async iterator）；临时文件在 finally 清理（`cleanupTempFile` 模式），异常路径不遗留。
- [ ] **磁盘稳健**：下载落盘前有空间检查或捕获 ENOSPC 转友好错误；目录递归创建（`mkdirSync recursive`）。
- [ ] **扩展名与 MIME**：扩展名来自内容探测（Content-Type/魔数）优先于 URL 后缀，防伪装文件。

### 5.7 上游容错与降级
- [ ] **多源降级**：核心链路（搜索/直链/歌词）多源可用时单源失败自动跳过（allSettled + errors 聚合），不因单源故障整体不可用。
- [ ] **重试幂等**：仅幂等操作（GET/查询）自动重试且有上限+退避；写操作（上传/评论）不自动重试防重复副作用。
- [ ] **熔断意识**：连续失败的上游（连续 N 次超时）短期短路直接返回降级响应，恢复探测后放行；至少以注释/TODO 标注熔断点。
- [ ] **错误信息分级**：上游错误转换为用户可读 msg + 内部 detail 分离，不把上游原始报错（含内部 URL/参数）直接暴露给前端。

### 5.8 幂等与一致性
- [ ] **写幂等**：重复提交同一写请求（双击/重试）不产生重复数据——唯一约束或预检（下载 `precheck` 模式）兜底。
- [ ] **读己之写**：前端写操作成功后的数据可见性有保证（同步返回最新状态或明确刷新通路）。
- [ ] **部分失败语义**：批量操作（批量收藏/删除）返回逐项结果（成功/失败清单），不静默丢弃失败项。
- [ ] **数据不变量**：跨表一致性（收藏数 ↔ 明细行数、下载记录 ↔ 磁盘文件）在事务内维护，对账差异可检测。

### 5.9 配置与环境
- [ ] **集中读取**：环境变量在专门模块读取并提供类型化默认值，禁止散落各文件 `process.env.X` 直取；未设置必需变量时启动即报明确错误。
- [ ] **运行时不可变**：配置加载后不因请求参数改写（请求级差异走参数传递，如 realIP/proxy 的注入路径）。
- [ ] **开关清理**：调试类开关（`NCM_DEBUG` 等）默认关闭；临时的功能开关上线前评审默认值并记录在报告中。
- [ ] **跨平台路径**：部署目标（Windows/Linux）均可运行——路径分隔符、大小写敏感文件名、ffmpeg 解析三级顺序均已覆盖。

### 5.10 进程内资源治理
- [ ] **缓存预算**：进程级缓存（apiCache、代理 dispatcher 池、公钥缓存）有 TTL + 容量上限 + 淘汰策略，并评估内存占用；大响应（>256KB）不缓存。
- [ ] **模块级状态**：模块级可变状态（`let xeapiSessionId` 类）登记清单，说明并发安全性与失效时机；多实例部署时此类状态的局限已知晓并记录。
- [ ] **定时器与句柄**：长驻定时器有清理通路；句柄（fd、子进程、AbortController）生命周期明确，无泄漏路径。
- [ ] **优雅退出**：SIGTERM 时在途写操作（下载落盘、数据库事务）可安全中断恢复，进程可正常退出不被悬挂句柄阻塞。

## 6. 前后端协同

- [ ] **契约单一来源**：请求/响应 TS 类型在 `lib/types.ts` 或共享 interface 定义，前端不得对后端结构做 `any` 断言；后端响应字段与类型声明一致（变更双侧同步修改）。
- [ ] **错误约定对齐**：后端错误结构（`{ error }` / 401 body）与前端处理（toast / loadError / 登录跳转）一一对应；401 的前端行为全局统一（提示登录而非静默失败）。
- [ ] **缓存语义一致**：前端 fetch 策略（`no-store`/默认）与后端 `force-dynamic`/响应缓存声明匹配，不得前端缓存了后端动态数据（或反之）导致脏读。
- [ ] **时序与超时兜底**：慢接口前端有骨架/加载态；前端超时提示与后端实际超时值（15s/10s 等）量级一致，不出现前端先放弃、后端仍成功的无反馈场景。
- [ ] **分页协议**：前后端分页参数与响应结构（page/pageSize/total/hasMore）约定统一，翻页组件与新接口直接对接无需适配层。
- [ ] **文档同步**：新增/修改接口同步更新 `README.md` API 对照表与专项文档（如 `docs/netease-api-inventory.md`）；环境变量新增同步前后端消费方说明。
- [ ] **全链路冒烟**：按附录 B 冒烟路径走通前后端真实链路（登录→搜索→播放→下载→新功能），重点核对本次变更的接口在前端的实际消费效果。
- [ ] **残留清理**：联调期的临时字段、console.log、mock 数据、注释掉的旧调用全部移出暂存区。
